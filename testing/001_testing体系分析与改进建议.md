# 凌栖项目测试体系分析与改进建议

> 预研方向：测试预研
> 分析时间：2026-09-06
> 覆盖范围：Ember（灵火）、Arboreus（建木）、Battleplan（战策）三仓库测试体系
> 参考前沿：Anthropic Agent评估体系（2026）、OpenAI Agent Evals、GzFuzz（ISSTA 2025）、OmniaBench（2026）

## 一、当前测试体系现状

### 1.1 三仓库测试概览

| 维度 | Ember（灵火） | Arboreus（建木） | Battleplan（战策） |
|------|--------------|-----------------|-------------------|
| 测试框架 | Node.js built-in `node --test` | tsx + Node.js built-in test | 自定义GDScript TestRunner |
| 测试文件数 | 48 | 85 | 7（含runner/scene） |
| 测试用例数（宣称） | ~1295 | ~1101 | ~265 |
| 组织方式 | 按认知子系统（tests/soul/） | 按功能系统（tests/根目录） | 按里程碑（M1/M2 IntegrationTest） |
| 运行命令 | `npm test` | `npm test` | Godot编辑器内运行 |
| CI集成 | 未知 | 未知 | 未知 |

### 1.2 Ember测试体系分析

**优势：**
- 覆盖面广：48个测试文件对应133个认知子系统，基本做到每个子系统有测试
- 命名清晰：测试文件与源文件一一对应（如`MetaAwareness.test.js`对应`MetaAwareness.js`）
- 按领域组织：`tests/soul/`目录集中管理，便于定位

**不足：**
- **缺少认知架构级别的集成测试**：当前测试以单个认知子系统的单元测试为主，缺少多子系统协同的端到端测试（如"感知→评估→决策→学习"完整认知循环）
- **缺少非确定性测试**：认知系统涉及随机因素和涌现行为，单次测试通过不代表稳定，需要pass@k/pass^k指标
- **缺少轨迹评估**：没有记录灵魂的完整决策轨迹（Transcript/Trace），无法评估"过程是否合理"，只能检查"结果是否正确"
- **缺少长期行为测试**：灵魂的成长、记忆巩固、人格演化等长期特性没有对应的长时程测试
- **缺少对抗性测试**：没有测试灵魂在异常输入、矛盾指令、极端情绪下的行为

### 1.3 Arboreus测试体系分析

**优势：**
- 测试数量最多（85个文件），覆盖感知、碰撞、导航、生态、建筑、叙事等核心系统
- 有M10多模态感知集成测试（`m10-multimodal-perception.test.ts`）
- 有跨系统集成测试（如`building-territory-perception.test.ts`、`party-perception.test.ts`）

**不足：**
- **缺少性能基准测试**：世界引擎需要处理大量实体和事件，没有性能回归基准（如"1000实体tick时间<10ms"）
- **缺少压力/负载测试**：没有测试系统在极限负载下的行为（如10000实体、每秒1000事件）
- **缺少模糊测试**：作为模拟器/引擎，Arboreus有庞大的状态空间和严格的输入格式，适合用GzFuzz式的语法感知模糊测试发现崩溃
- **缺少确定性/可复现性测试**：模拟系统需要确定性，没有测试"相同种子+相同输入=相同输出"
- **缺少混沌测试**：没有测试系统在组件故障、网络延迟、资源不足时的降级行为

### 1.4 Battleplan测试体系分析

**优势：**
- 有里程碑级集成测试（M1/M2 IntegrationTest）
- 265个测试用例全绿，平台层重构后保持稳定

**不足：**
- **测试文件过少**：7个文件承载265个用例，单文件过大，难以维护和定位
- **缺少单元测试**：以集成测试为主，缺少单个系统（音频、网络、UI、战斗逻辑）的单元测试
- **缺少游戏平衡测试**：RTS游戏的平衡性（兵种克制、经济曲线、胜率）没有自动化测试
- **缺少网络同步测试**：服务端权威架构下，没有测试客户端预测/回滚、延迟补偿、断线重连
- **缺少性能测试**：没有帧率、内存、网络带宽的基准测试

## 二、前沿测试方法论追踪

### 2.1 AI Agent评估体系（Anthropic 2026 + OpenAI Agent Evals）

**核心思想**：AI Agent的评估不能只检查最终输出，而要同时评估**任务、运行轨迹、工具调用、外部环境结果和多次运行的稳定性**。

**八个核心评估对象：**
| 对象 | 定义 | 对Ember的映射 |
|------|------|--------------|
| Task | 有明确输入与成功条件的测试任务 | "灵魂在恐惧刺激下做出合理决策" |
| Trial | Agent对某个任务的一次运行 | 灵魂的一次完整认知循环 |
| Grader | 对运行结果评分的逻辑 | 断言+规则评分器 |
| Transcript/Trace | 一次运行的完整交互轨迹 | 灵魂的感知→评估→决策→行动完整记录 |
| Outcome | 运行结束时外部环境的最终状态 | 灵魂最终采取的行动和世界状态变化 |
| Evaluation Harness | 运行/记录/评分/汇总的基础设施 | 测试运行器 |
| Agent Harness | 让模型规划和调用工具的运行框架 | Ember的认知循环执行器 |
| Evaluation Suite | 围绕某类能力组织的任务集合 | 按认知能力组织的测试套件 |

**三类评分器组合：**
1. **代码评分器**：字符串匹配、单元测试、数据库状态检查——速度快、可重复，适合确定性事实
2. **模型评分器（LLM-as-a-Judge）**：对完整性、交互质量、解释质量评分——适合开放性任务，但需校准
3. **人工评分器**：领域专家复核——成本最高，用于高风险场景校准

**pass@k vs pass^k：**
- `pass@k = 1 - (1-p)^k`：k次运行至少成功一次，适合探索性任务
- `pass^k = p^k`：连续k次全部成功，适合生产级稳定性要求
- 单次成功率75%时，pass@3≈98.4%，但pass^3≈42.2%——一次成功案例不能证明系统可靠

**双层断言（对Ember最有价值）：**
- **Outcome Assertion**：检查灵魂最终采取的行动是否合理
- **Trajectory Assertion**：检查灵魂的决策过程是否合理（是否调用了正确的认知子系统、是否考虑了相关因素、是否有逻辑跳跃）

### 2.2 模拟器模糊测试（GzFuzz, ISSTA 2025杰出论文）

**核心思想**：针对Gazebo机器人模拟器这类有严格输入语法和庞大状态空间的系统，传统模糊测试（AFL++）因输入格式错误被立即拒绝而无效。GzFuzz提出：
1. **语法感知的可行命令生成**：确保生成的测试命令在语法和语义上符合系统要求
2. **强化学习智能选择命令生成器**：在庞大状态空间中有效探索深层执行路径
3. **效果**：代码覆盖率提升234%-360%，半年发现25个崩溃故障（24个已确认/修复）

**对Arboreus的直接映射**：
- Arboreus作为世界模拟器，有严格的事件格式、实体状态约束和系统接口
- 可以设计语法感知的事件序列生成器，自动生成合法但异常的事件序列
- 用强化学习引导探索，发现导致崩溃、死锁、状态不一致的输入
- 特别适合测试：事件系统、实体生命周期、感知系统边界条件、保存/加载一致性

### 2.3 其他前沿方向

- **OmniaBench（2026.07，华为云+北大）**：面向通用AI Agent的"全身体检"基准，覆盖真实应用场景
- **智能体长期记忆评测（2026.08，openKylin）**：专门评估Agent的记忆能力——记不住、记太死都是问题
- **TPDD与高层测试闭环（2026.03）**：AI开发时代的测试方法论，提前明确预期行为、优先级、测试覆盖范围
- **精准测试能力成熟度模型（2025，中国信通院）**：从传统测试向智能化精准测试演进

## 三、改进建议（按优先级排序）

### P0：立即可以做的改进

#### 1. 建立测试覆盖率报告
- Ember和Arboreus接入`c8`或`nyc`生成覆盖率报告
- 设定最低覆盖率门槛（如语句覆盖>80%，分支覆盖>70%）
- 每次CI运行生成覆盖率趋势图
- **价值**：量化测试完整性，发现未覆盖的代码路径

#### 2. Ember引入认知循环集成测试
- 设计"完整认知循环"测试场景：给定初始世界状态和刺激，验证灵魂从感知→评估→决策→行动→学习的完整流程
- 每个测试场景记录完整Trajectory（感知帧、评估结果、决策路径、行动选择、学习更新）
- 引入双层断言：Outcome（行动是否合理）+ Trajectory（过程是否合理）
- **价值**：当前单元测试无法发现的子系统间交互bug

#### 3. Battleplan拆分测试文件
- 将7个大文件拆分为按系统组织的测试文件（audio.test.gd、network.test.gd、combat.test.gd等）
- 保持M1/M2集成测试作为顶层回归测试
- **价值**：提高可维护性，便于定位失败

### P1：下一阶段应该做的改进

#### 4. Ember引入非确定性测试与pass@k指标
- 对涉及随机因素和涌现行为的测试，运行N次（如N=10），报告pass@1和pass@5
- 设定稳定性门槛：核心认知功能pass@5 > 95%
- 记录失败轨迹用于分析
- **价值**：发现"偶尔失败"的隐蔽bug，避免单次通过的虚假信心

#### 5. Arboreus建立性能基准测试
- 定义标准基准场景：N个实体（100/500/1000/5000）、M个事件/秒、运行T个tick
- 测量：tick平均时间、P99时间、内存占用、GC频率
- 每次PR运行基准测试，与基线对比，性能退化>5%则告警
- **价值**：防止性能退化，为优化提供数据支撑

#### 6. Arboreus引入确定性/可复现性测试
- 核心模拟逻辑必须支持种子化随机数
- 测试：相同种子+相同输入序列→完全相同的输出状态
- 保存/加载测试：保存状态→加载→继续模拟→与不保存的结果一致
- **价值**：模拟器的核心质量属性，bug可复现是调试的前提

#### 7. Battleplan建立游戏平衡测试框架
- 定义标准对战场景：固定地图、固定资源、AI vs AI
- 运行大量自博弈（如100局），统计：胜率、平均时长、经济曲线、兵种使用率
- 平衡性指标：胜率偏离50%不超过5%，无单一兵种使用率>40%
- **价值**：RTS游戏的核心竞争力，自动化平衡测试替代人工试错

### P2：中长期探索方向

#### 8. Arboreus语法感知模糊测试（借鉴GzFuzz）
- 定义Arboreus事件/命令的语法规范
- 实现语法感知的事件序列生成器
- 用强化学习引导探索高覆盖率路径
- 目标：发现崩溃、死锁、状态不一致、内存泄漏
- **价值**：主动发现边界条件bug，而非等待用户报告

#### 9. Ember灵魂行为长时程评估平台（借鉴Emergence World）
- 持续运行的灵魂模拟沙盒，运行数天/数周
- 追踪指标：人格稳定性、记忆衰减曲线、学习迁移效果、社会关系演化、行为漂移
- 定期生成灵魂"体检报告"
- **价值**：发现长期运行才会显现的问题（记忆膨胀、人格漂移、学习饱和）

#### 10. 跨引擎端到端集成测试
- Ember灵魂 + Arboreus世界 + Battleplan对战的完整链路测试
- 验证：灵魂在Arboreus世界中感知→决策→行动，行动结果通过Battleplan呈现
- 测试SDK接口兼容性（Ember SDK v1.8.0 + Arboreus SDK v2.5.0/v2.6.0）
- **价值**：确保三引擎协同工作，接口变更不破坏集成

#### 11. 混沌测试框架
- 模拟组件故障：数据库断开、网络延迟、内存不足、CPU限流
- 验证系统的降级和恢复能力
- 特别关注：Ember的认知优雅降级、Arboreus的状态一致性、Battleplan的断线重连
- **价值**：提高生产环境的鲁棒性

#### 12. 突变测试（Mutation Testing）
- 对核心逻辑代码引入微小变异（如`>`改为`>=`、`+`改为`-`）
- 运行测试，检查是否能杀死变异
- 突变存活率高的代码说明测试质量不足
- **价值**：评估测试本身的质量，而非仅看覆盖率

## 四、测试金字塔重构建议

当前三仓库的测试分布偏向上层（集成测试多，单元测试和性能测试少）。建议重构为健康的测试金字塔：

```
                    ┌─────────────┐
                    │  E2E/探索性  │  跨引擎端到端、长时程模拟、混沌测试
                    │   测试 (5%)  │
                    ├─────────────┤
                    │  集成测试    │  认知循环、多系统协同、对战流程
                    │  (15%)      │
                   ┌┴─────────────┴┐
                   │   单元测试     │  各子系统/模块的独立测试（当前主体）
                   │   (60%)       │
                  ┌┴───────────────┴┐
                  │  性能/基准/确定性 │  性能基准、可复现性、压力测试
                  │    测试 (20%)    │
                  └─────────────────┘
```

**关键转变**：
- 从"只有功能测试"到"功能+性能+确定性+稳定性"四维测试
- 从"单次通过"到"pass@k稳定性"
- 从"只检查结果"到"结果+轨迹双层断言"
- 从"被动发现bug"到"模糊测试主动探索bug"

## 六、风险与注意事项

1. **测试本身的维护成本**：更多测试意味着更多维护工作，需要平衡覆盖率和可维护性
2. **非确定性测试的flakiness**：引入pass@k后，需要区分"真正的bug"和"可接受的随机性"
3. **性能基准的环境噪声**：开发机性能不稳定，基准测试需要在固定环境运行
4. **模糊测试的时间成本**：强化学习引导的模糊测试需要大量计算资源，应在夜间/周末运行
5. **LLM-as-a-Judge的偏差**：如果Ember引入模型评分器，需要定期用人工样本校准
6. **不要为了测试而测试**：测试的目的是发现bug和保证质量，不是追求数字
