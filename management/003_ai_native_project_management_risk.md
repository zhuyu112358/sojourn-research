## 一、研究背景

凌栖管理体系已从第5轮的基础诊断（7个定时任务+23节管理策略+仪表盘）发展到第10轮的知识管理深化（RAG/GraphRAG+AI协作效率+DORA/SPACE度量）。当前管理体系包括：

- **7个定时任务**：监控/预研/Ember/Arboreus/战策/集成测试/管理（每3小时轮询）
- **管理策略文档**：24节，约50KB，覆盖项目全生命周期
- **管理仪表盘**：6模块（总览/任务/仓库/资源/历史/文档），http://localhost:3001
- **Bug跟踪**：BUG-001~019全部关闭，活跃bug 0
- **双SDK**：Ember SDK v1.8.0 + Arboreus SDK v2.6.0
- **预研体系**：18轮预研，284项未实现方向，60条游戏设计数据库

但2026年AI项目管理正在发生范式变革：
- **从AI辅助到AI原生**：AI不再是工具，而是项目管理的一等参与者（Agentic PM）
- **从被动分析到主动预警**：多Agent系统主动监控风险、预测延误、建议调整
- **从人工知识管理到知识策展Agent**：AI自动从所有项目产物中提取、分类、关联知识
- **从季度评估到持续验证**：AI模型和Agent的性能需要持续验证，而非上线前一次测试
- **从功能风险到AI特有风险**：幻觉、模型降级、Agent失控、数据投毒等新型风险

本报告追踪这些前沿，分析凌栖当前管理体系的差距，提出AI原生管理的融合改进方案。

## 二、前沿追踪：2026 AI原生项目管理

### 2.1 多Agent项目管理系统

**PMO-APEX研究系统**（学术前沿）：
- 编排48个专业Agent覆盖项目全生命周期
- 调度Agent监控时间线和依赖关系
- 资源Agent追踪团队成员可用性
- 风险Agent基于历史延误和依赖图谱触发预警
- 质量Agent监控交付物质量和测试覆盖率

**Orchestrator架构模式**：
- 各专业Agent不直接互通，通过Orchestrator（协调器）做任务拆解、路由和冲突仲裁
- 共享Memory层维持上下文一致性
- 与微服务架构中"数据库集成优于直接消息传递"的设计哲学同源
- MCP（Model Context Protocol）作为Agent读写项目数据的标准接口层

**Agentic项目管理工作流**（Observe→Compare→Distill→Propose）：
1. **Observe**：系统接收新信号（会议记录/文档/聊天/任务更新）
2. **Compare**：Agent将信号与当前项目上下文对比
3. **Distill**：识别信号是否改变目标/需求/风险/时间线/预算/行动项
4. **Propose**：创建具体的更新建议，人类在决策点审批

**商业产品动向**：
- **Asana AI Studio**（2026）：无代码工作流构建器，AI Agent直接嵌入流程，"campaign strategist"/"spec reviewer"/"brief checker"等AI队友
- **ChatGPT Workspace Agents**（2026.4）：团队创建共享Agent处理复杂任务和长运行工作流，在组织权限和控制内运行
- **ONES.com**：软件开发管理Agent直接内建在工作区，自然语言查询项目数据

**对凌栖的启示**：
- 当前7个定时任务本质上是7个单Agent，缺乏Orchestrator层协调
- 任务间依赖靠管理策略文档人工维护，没有自动的依赖图谱和冲突仲裁
- 可以引入"监控Agent"升级为Orchestrator——不仅监控，还主动协调各任务间的依赖和冲突

### 2.2 知识策展Agent（Knowledge Curation Agent）

**从RAG到知识策展**：
- 第一代RAG：人工维护知识库，AI检索回答
- 第二代（2026）：知识策展Agent自动消费所有项目产物——设计文档、代码提交、邮件线程、聊天记录、会议转录、最终报告
- 使用NLP方法（主题建模、命名实体识别）自动存储、分类和关联知识
- 主动发现知识缺口、过期信息和重复内容

**知识策展Agent的核心能力**：
| 能力 | 说明 |
|------|------|
| 自动索引 | 所有新文档/代码/讨论自动索引到知识库 |
| 实体识别 | 自动识别人物/系统/概念/任务等实体并建立关联 |
| 过期检测 | 检测与当前状态矛盾的旧文档，标记为过期 |
| 知识缺口 | 识别应该有但缺失的文档（如某子系统无设计文档） |
| 关联推荐 | 自动发现文档间的隐含关联，建立知识图谱 |
| 摘要生成 | 为长文档自动生成结构化摘要和关键决策记录 |

**对凌栖的启示**：
- 当前预研仓库有60+数据库条目、18+研究报告、24节管理策略，但知识关联靠人工维护（DATABASE_INDEX的跨主题关联）
- 可以引入知识策展Agent自动维护索引和关联网络
- 管理策略文档24节约50KB，需要自动检测过期内容（如各轮任务prompt中的状态描述已过时）

### 2.3 AI生产环境风险管理

**四类AI错误模式**（Kognitos, 2026生产环境分析）：

| 错误模式 | 描述 | 检测信号 | 修复路径 |
|---------|------|---------|---------|
| **幻觉（Hallucination）** | AI编造不存在的事实，看似合理 | 事实核查失败、引用不存在的来源 | RAG grounding + 输出验证 |
| **漂移（Drift）** | 模型性能随时间/输入分布变化而下降 | 持续验证指标下降、用户反馈变差 | 持续模型验证+自动回滚 |
| **失控（Loss of Control）** | Agent执行超出预期的多步操作，造成破坏 | 工具调用序列异常、权限越界 | 每步审批+操作白名单+熔断 |
| **过度自信（Overconfidence）** | AI对错误答案给出高置信度 | 置信度校准偏差、高置信低正确率 | 置信度阈值+人工审核高风险输出 |

**RAG的幻觉降低效果**（2026年2月企业供应商联盟数据，847个生产部署）：
- 中位数降低71%，范围58%-89%（取决于检索语料质量和分块策略）
- 关键实现要求：检索置信度阈值、分块策略优化、引用溯源

**SITS2026攻防演练发现的6类隐性风险**：
1. Token截断导致历史遗忘（80%安全水位截断尾部，幻觉率提升3.7倍）
2. 提示词注入通过用户输入传播
3. 模型降级时无自动切换（API限流/降级导致质量骤降）
4. Agent工具调用权限过大（shell_execute/file_write无审批）
5. 多Agent协作中的错误传播（一个Agent的错误输出被另一个Agent当作事实）
6. 训练数据投毒（微调数据被污染）

**应急熔断机制**：
- 触发条件：幻觉率>阈值、响应时间>阈值、错误率>阈值、工具调用异常模式
- 熔断动作：降级到规则引擎、切换备用模型、暂停Agent自动执行、通知人工
- 恢复条件：指标恢复正常+人工确认

**持续模型验证流水线**：
- 不是季度验证，不是上线前验证，而是**持续验证**
- 每次模型更新/配置变更自动运行验证套件
- 验证维度：事实准确性、安全性、延迟、成本、角色一致性
- 验证失败自动阻止部署或触发回滚

**OpenAI Astra监控先例**（2026.8）：
- 对Sol一级能力的工具调用RL训练和评测，必须接入监控
- 检查工具动作、可见推理过程、完整事件序列
- 寻找：越权访问、数据窃取、破坏性操作、绕过防护的痕迹

**对凌栖的启示**：
- 当前7个定时任务都是AI Agent，但缺乏Agent级别的风险管理
- 没有持续模型验证——大模型调用质量靠人工感知，没有量化指标
- 没有熔断机制——模型API故障时任务直接失败
- 定时任务的AI输出（如预研报告）没有幻觉检测
- Ember的ValueGuard是内容安全，但不是Agent行为安全

## 四、不足诊断：10项新差距

### 4.1 管理架构：无Orchestrator层

**差距1：7个定时任务是独立Agent，无协调层**
- 任务间依赖靠管理策略文档人工维护
- 没有自动的依赖图谱——Ember任务修改了SDK接口，Arboreus/战策任务不会自动收到通知
- 没有冲突仲裁——两个任务同时修改同一文件时无协调
- 没有全局优先级——任务都是每3小时执行，无法根据项目阶段动态调整频率

### 4.2 知识管理：人工维护索引

**差距2：知识库索引和关联全靠人工**
- 预研仓库的RESEARCH_INDEX、DATABASE_INDEX、unimplemented_directions都是人工更新
- 每轮预研需要手动更新3个索引文件，容易遗漏
- 文档间的关联靠人工发现（如DATABASE_INDEX的跨主题关联）
- 没有自动的过期检测——管理策略中各任务prompt的状态描述已过时但未更新
- 没有知识缺口检测——某些子系统可能缺乏设计文档

### 4.3 AI风险管理：几乎空白

**差距3：定时任务AI输出无幻觉检测**
- 预研报告、管理报告、代码分析等AI输出没有自动幻觉检测
- 报告中的事实性陈述（如"某论文发表于某会议"）无法自动验证
- 参考第17轮HCPD幻觉检测方法，可以集成到任务输出验证中

**差距4：无持续模型验证**
- 大模型调用质量没有持续监控——模型降级/API变更时无法感知
- 没有模型性能基线和漂移检测
- 没有A/B测试框架对比不同模型在任务中的表现

**差距5：无Agent行为安全机制**
- 定时任务有文件写入权限，但无操作白名单和审批
- 没有熔断机制——模型API故障/异常输出时任务继续执行可能产生错误结果
- 没有工具调用审计——任务执行了哪些操作、修改了哪些文件，没有完整日志

### 4.4 度量体系：偏数量轻质量

**差距6：度量以数量为主，缺乏质量和效率指标**
- 当前度量：测试用例数、子系统数、代码行数、预研轮数
- 缺乏：需求交付周期、缺陷逃逸率、AI输出质量评分、任务执行效率
- 缺乏DORA四指标（部署频率/变更前置时间/变更失败率/恢复时间）
- 缺乏SPACE框架（满意度/绩效/活动/沟通/效率）

### 4.5 风险管理：无主动预警

**差距7：风险管理是被动的，无主动预警**
- Bug跟踪是事后的——bug出现后才记录
- 没有基于历史数据的风险预测——哪些模块容易出bug、哪些任务容易延期
- 没有依赖风险图谱——SDK接口变更的影响范围分析
- 没有技术债量化和预警

### 4.6 任务执行：无效率优化

**差距8：定时任务执行效率低**
- 7个任务每3小时全部执行，不管是否需要
- 任务间有大量重复工作（如每个任务都要读取管理策略、检查仓库状态）
- 没有增量执行——每次都是全量扫描
- 没有任务结果缓存——相同输入重复计算

### 4.7 沟通协作：无结构化决策记录

**差距9：决策记录分散，缺乏结构化管理**
- 项目决策散落在管理策略文档、DEVLOG、commit message、聊天记录中
- 没有ADR（Architecture Decision Record）体系——重要技术决策没有结构化记录
- 决策的上下文、选项、理由、后果没有系统整理
- 新任务启动时需要重新理解历史决策

### 4.8 资源管理：无成本量化

**差距10：AI调用成本无量化管理**
- 7个定时任务+开发过程中的大模型调用没有成本统计
- 没有按任务/仓库/功能维度的成本分析
- 没有成本优化建议——哪些调用可以缓存、哪些可以用更便宜的模型
- 参考第18轮数据收集体系的大模型成本跟踪，但管理侧尚未建立

## 六、三阶段路线图

### 阶段一：管理基础增强（M11内，P0）
- 目标：从"人工管理"升级到"半自动管理+AI质量保障"
- 关键交付：Orchestrator原型、索引自动更新、幻觉检测、成本统计、ADR体系、熔断机制
- 验收标准：索引更新自动化率>80%，任务异常熔断触发测试通过，ADR目录建立

### 阶段二：AI原生管理（M12，P1）
